# الدفعة الحالية — مطابقة المتطلبات وحماية إعداد الهاردوير

> هذه نتائج الدفعة البرمجية المحفوظة في `progress/history/safeguards-20261124.json`.
> الطلب الأحدث هو رفع ESP32 واختبار USB؛ حالته الحية في `progress/state.json`
> وبدأ بعد تأكيد المستخدم مراجعة USB فقط وفصل كل المكونات وتفويض FLASH.
> المحاولة توقفت عند read-mac بخطأ `0x56` قبل backup والكتابة؛ لم يُجرَ اختبار الكاميرا.
> النطاق والبوابات في `usb-flash-batch.md`؛ لا اعتماد لتوصيل المكونات السابق.

## النطاق والحدود

استكمال المشروع الموجود، لا استبدال `../esp32cam_live/` ولا تغيير الأدوات أو
تثبيت تبعيات. وصف المستخدم الحالي **غير معتمد كهربائيًا**: إغلاق تلامس بين
L وN قصر مباشر، GPIO16 يتعارض مع PSRAM، GPIO12 طرف اختيار جهد الفلاش، ولم
تُذكر مقاومة تحديد تيار للـIR LED. لا فلاش أو فتح serial أو تشغيل حمل في الدفعة.

النسخة الأولى تحتفظ بالرؤية على اللاب وبـFlutter Android عبر BLE. النوم وضع
صريح مؤقت، والإعلان قابل للرصد خارج التطبيق، والتحكم بالتكييف مفتوح الحلقة.

## المهام وفحوص القبول

1. **requirements** — مراجعة `firmware/smart_room/`, `app/lib/`, `host/`، وكتابة
   `docs/requirements.md` مع حدود BLE والنوم ودقة العدّ. تحديث `docs/hardware.md`
   بتعارضات وصف المستخدم ومراجع Espressif، دون تعليمات توصيل mains تنفيذية.
2. **board-guard** — إضافة سياسة أطراف محلية واختبارات compile سلبية وضوابط
   صالحة؛ دمجها في `board_config.h`. المخارج تظل معطلة. لا قبول للأطراف المحجوزة
   أو GPIO12 أو ازدواج أدوار الأطراف أو تفعيل دوائر غير مراجعة.
3. **launcher** — توفير ملف تشغيل Windows بنقرة مزدوجة داخل المشروع، مع إبقاء
   مصدر الفيرموير والـhelper منفصلين. تحسين الرفض والتعامل مع فشل الأدوات؛ اختبار
   الفحص والإلغاء فقط، دون `-ConfirmHardwareReviewed` على منفذ حقيقي.
4. **verification** — تنفيذ اختبارات Python باستخدام Python 3.14 الموجود،
   اختبارات C++ والعقد، ثم compile للفيرموير دون upload، والتحقق من بصمات
   الملفات الأصلية. تحديث `README.md`, `EVIDENCE.md` وسجل التقدم بنتائج فعلية.

أوامر أساسية (من جذر المشروع):

```powershell
py -3.14 -m unittest discover -s tests -v
py -3.14 tools/run_contract_tests.py
g++ -std=c++17 -Wall -Wextra -Werror -pedantic tests/core_tests.cpp -o <owned-temp>/core.exe
arduino-cli compile --fqbn esp32:esp32:esp32cam:PartitionScheme=huge_app --build-path <owned-temp>/cache --output-dir <owned-temp>/out firmware/smart_room
```

نجاح الاختبارات لا يعتمد توصيلًا أو جهدًا أو قطبية أو سلامة mains. الاقتران
الحقيقي والتعلّم/الإرسال ودقة الغرفة بوابات منفصلة. سجل الدفعة السابقة محفوظ
في `progress/history/software-20261124.json`؛ عدّ مهام هذه الدفعة مستقل عنه.

## قرارات التشغيل وحدودها

- مدخل `.cmd` يفتح قائمة PowerShell فقط. لا تمرير لتأكيد الأجهزة أو تخطي النسخة
  الاحتياطية من الملف بنقرة مزدوجة، ولا تغيير سياسة التنفيذ. البديل: `.ps1`
  وحده كان يترك المستخدم مع أوامر يدوية ولا يحقق طلب المدخل السهل.
- `Invoke-Native` يستخدم `ProcessStartInfo` وargv quoting بدل مسار PowerShell
  الذي يفقد علامات الاقتباس وقد يعتبر stderr استثناءً. قراءات stdout/stderr
  متزامنة بصورة غير حاجبة، بسعة محدودة ومهلة. Windows Job خاص يملك العملية
  وأبناءها بعد إلحاقها مباشرة عند start؛ هذا ليس sandbox. الفشل قبل الإلحاق
  أو أثناء cleanup يفشل التشغيل، ولا يثبت اكتمال كتابة. لا قتل للـviewer.
- كل بناء له مجلد إخراج جديد؛ `-CleanBuild` يستخدم كاشًا جديدًا بدل مسح القديم.
  البناء بعاملين فقط. يتطلب مسار الرفع MAC مطابقًا حتى عند إلغاء backup، ويعيد
  فحص المصدر/بصمات ملفات البناء/الهوية بعد `FLASH`؛ هذا ليس حماية ضد خصم محلي
  يغير الملفات في نافذة زمنية ضيقة ولا تحققًا لشكل البورد من MAC وحده.
- فحص const flags محافظ وليس محلل C++ كاملًا؛ التعليقات والنسخ المتعددة أو
  التعبيرات ليست إثباتًا أن المخارج false. يظل compiler هو بوابة سياسة الأطراف
  و`HARDWARE_REVIEWED`؛ أي من هذين إقرار برمجي لا مراجعة كهربائية.

تغطي fixtures الخاملة quoting وstderr والمهلة وحجم الخرج وأبناء العملية حتى
بعد انتهاء الأب، ورفض هوية الشيب والأطراف. بوابة فلاش فعلي لم تُنفذ.
